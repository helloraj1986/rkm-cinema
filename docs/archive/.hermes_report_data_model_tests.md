- `year` (int) — release year. Real: `2016`.
- `category` (str) — one of the 12 rotation categories. Real: `"Sci-Fi/Fantasy"`. (Repo-sample entries carry `category: "Comedy"`, `"Action"`, `"Thriller"`, `"Drama"`.)

- `imdbId` (str) — canonical IMDb id, always `tt`-prefixed. Real: `"tt2543164"`.
- `tmdbId` (int) — TMDB id. Real: `329865`. **Both `imdbId` and `tmdbId` are used for dedup in `add_pending`** (gotcha §6).

- `director` (str) — Real: `"Denis Villeneuve"`.

- `trailerId` (str) — YouTube video id, NOT a full URL. Real: `"7W1m5ER3I1Y"`. Repo IMC sample: `"oGI9hSl0q-w"`, `"VPDErRzsl-0"`, `"2SupordEUpw"`.
- `trailerTitle` (str) — YouTube title. Real: `"Final Trailer"`. Repo sample: `"ARRIVAL | Official Trailer"`, `"Mad Max: Fury Road (2015) Official Trailer [HD]"`.
- `added` (str) — ISO date `YYYY-MM-DD`. Real: `"2026-08-17"`, `"2026-08-18"`. This is the date used as `added_at` in SQLite.
- `tmdb_overview` (str, default `""`) — TMDB long synopsis (optional enrichment). Real: Arrival's TMDB overview.
- `backdrop` (str, default `""`) — TMDB w1280 backdrop URL. Real: `https://image.tmdb.org/t/p/w1280/8MUZz7oPXQftFTslZpRP3CVMOoq.jpg`.
- `tmdb_score` (float, default `0.0`) — TMDB vote average (0–10). Real: `7.632`. Frontend maps it to camelCase `tmdbScore` for the modal.
- `runtime` (int, default `0`) — minutes. Real: `0` for Arrival (i.e. not yet enriched).
- `genres` (list[str], default `[]`) — genre names (not ids). Real: `["Drama","Science Fiction","Mystery"]`.
- `source` (str, default `"user"`) — provenance of the entry (`"user"` manually added; recommendation/auto-add pipeline entries may carry other markers).
- `state` (str, default `"pending"`) — lifecycle state. Valid set in `VALID_STATES` (services/watchlist.py lines 18–26): `pending, requested, downloading, downloaded, available, failed, recommended`. All 296 live entries are currently `"pending"`.
- `completed` (str|None, default None) — `YYYY-MM-DD` set when moved to `recommended` via `move_to_recommended` / `update_status`.
- `detail` (str, default `""`) — human free-text status detail.
- `progress` (int, default `0`) — download progress percent (0–100).

**Repo-sample divergence (schema drift to note):** a couple of the 7 sample entries show `trailer` (full YouTube **search URL**) instead of `trailerId`/`trailerTitle`: e.g. Whiplash has `"trailer": "https://www.youtube.com/results?search_query=Whiplash+2014+trailer"` and no `trailerId` — clearly an older/fallback shape. The production data (and the current `WatchlistEntry` model) always uses `trailerId` + `trailerTitle`. The repo sample is not representative of the live model.

**State machine** (`VALID_STATES` + `VALID_TRANSITIONS`, lines 29–37): `pending→{requested, failed, recommended}`, `requested→{downloading, downloaded, failed, available}`, `downloading→{downloaded, failed, available}`, `downloaded→{available, failed}`, `available→{recommended}`, `failed→{pending, requested}`, `recommended→{}` (terminal). `update_status` validates state membership and transition legality, raising `WatchlistError`/`StateTransitionError` on violations; transitioning to `recommended` moves the entry pending→recommended list. Dict restoration uses `WatchlistEntry.from_dict`, which backfills every required field default and filters to annotated keys.

## 3. SQLite migration — status and how live it is

**SQLite IS live in production.** The `.env` file at `/workspace/.env` was readable and contains:

```
WATCHLIST_STORE=sqlite
WATCHLIST_DB_PATH=/workspace/media/watchlist.db
```

`config/settings.py` reads `WATCHLIST_STORE` (defaults to `"json"`, coerces any value other than `"json"|"sqlite"` back to `"json"`) and `WATCHLIST_DB_PATH`. Because it's the canonical `.env` and also overridable by process env, the effective store is `sqlite`.

The live DB `/workspace/media/watchlist.db` exists (921,600 bytes) in WAL mode (note the `watchlist.db-shm` / `watchlist.db-wal` files in `/workspace/media/`). Live row counts queried directly:

- `media`: **539**
- `watchlist`: **416** (of which `active=1, state='pending'` = 415, plus 1 `active=0, state='meta'` row)
- `recommendations`: **506** (the seen-history set, spec §23)
- `library_items`: 0 · `acquisitions`: 0 · `watch_links`: 0 · `job_runs`: 0 (tables exist, empty)

**Discrepancy / staleness warning:** the DB reports **415** active pending rows, but both the mirror `watchlist.json` and `dashboard-data.json` reflect only **296** pending. The mirror/dashboard snapshots date from `Sep 2 11:01` while the DB is actively written (files touched `Sep 3–4`). So **SQLite is the authoritative, actively-updated store; the JSON mirror and dashboard snapshot lag it** and should be regenerated for a fully current picture.

### Migration mechanics (`scripts/migrate_json_to_sqlite.py`, 110 lines)

Behavior (single `main()`, idempotent):
1. Loads canonical JSON via `JsonWatchlistRepository().load()`; if `pending==0 and recommended==0` it refuses (`sys.exit(1)`).
2. Resolves target via `SqliteWatchlistRepository()` (uses `WATCHLIST_DB_PATH`). Prints `[store=...]` and **warns** if `WATCHLIST_STORE != "sqlite"` (the app would keep reading JSON).
3. **Backs up** an existing SQLite DB to `<path>.bak-YYYYmmdd-HHMMSS` before writing (two such backups already exist in `/workspace/media/`).
4. `dst.save(raw)` writes meta + all entries.
5. **Carries the recommendation history** (sidecar JSON → SQLite `recommendations`) via `record_recommendation` per row.
6. **Round-trip verifies** entry counts (pending & recommended) and aborts (`sys.exit(1)`) on mismatch.
7. **Re-exports** `raw` back to `watchlist.json` as a one-time mirror ("generated export, not authoritative").
8. **Rebuilds** the dashboard via `scripts/rebuild_dashboard.py` `build()`, printing card count.

### Repository layer (`infrastructure/database/repository.py`, 375 lines)

`WatchlistRepository` ABC with two impls selected by `build_repository(store)`:
- `JsonWatchlistRepository` — atomic `tmp` + `os.replace` writes with an mtime cache; path resolves to `/app/watchlist.json` (container) else `/workspace/media/watchlist.json`; keeps recommendation history in a sidecar `recommendations_history.json` (`_HISTORY_CAP=3000`).
- `SqliteWatchlistRepository` — one row per entry in `watchlist`, keyed by canonical `media_id` (`_media_id_for`: `"tv|movie:tmdb:<int>"` → `"tv|movie:imdb:tt..."` → `"tv|movie:tvdb:<int>"` → title fallback `"type:title:<...>"`). Rich fields live in the JSON `payload` column; `media_id="__meta__"` row stores `{rotation_index, rotation, updated, hero_mode}`. Pending = `active=1`, recommended history = `active=0`. `save()` does `DELETE FROM watchlist WHERE media_id != '__meta__'` then re-inserts everything — idempotent, no dupes. Also has `job_runs` and `recommendations` tables.

### DB schema (`infrastructure/database/db.py`, 161 lines)

Stdlib `sqlite3`, hand-rolled `_SCHEMA`, tables: `media(id PK, media_type, title, year, tmdb_id, imdb_id, tvdb_id, created_at, updated_at)`, `watchlist(media_id PK→media, active, reason, criteria_score, priority, added_at, updated_at, state, payload JSON)`, `recommendations(media_id, first_seen, last_seen, decision, score, payload, PK(media_id))`, `library_items`, `acquisitions`, `watch_links`, `job_runs`. WAL journal mode; thread-local connections; `get_database()` lazy singleton.

**Summary:** migration is **complete and live** — store is `sqlite`, DB populated (415 pending active + 506 history rows), JSON kept only as a mirror. The only caveat is snapshot freshness (§3 discrepancy).

## 6. Gotchas

1. **Two `watchlist.json` files — don't confuse them.** `/workspace/projects/rkm-cinema/watchlist.json` is a 7-entry dev sample; the real dataset is the 296-entry mirror at `/workspace/media/watchlist.json` beside the live DB. Editing the repo sample does nothing to production.
2. **SQLite is already the live store** (`WATCHLIST_STORE=sqlite`, DB at `/workspace/media/watchlist.db`). JSON is a generated mirror only. But the mirror/dashboard snapshot **lag**: DB says 415 active pending, mirror+dashboard say 296 → snapshots are stale days behind; regenerate (`scripts/rebuild_dashboard.py`) after any DB write to resync.
3. **Dedup is by BOTH imdb and tmdb.** `WatchlistService.add_pending` raises `DuplicateError` if the new entry's `imdbId` OR `tmdbId` already appears (find_by_imdb / find_by_tmdb). The pipeline also excludes everything already in Plex (ownership gate) and the `recommendations` seen-set (spec §24 idempotency, `_HISTORY_CAP=3000`).
4. **Atomic writes everywhere.** JSON store (`JsonWatchlistRepository.save`) and the history sidecar both write `*.tmp` then `os.replace`; corruption raises `WatchlistError`. The SQLite repo instead clears+re-upserts the `watchlist` table on each `save()` (idempotent, no dupes).
5. **Canonical media_id format** `{type}:{provider}:{id}` i.e. `movie:tmdb:<int>`, `tv:imdb:tt...`, `tv:tvdb:<int>`, fallback `type:title:<...>`. The frontend `mediaIdOf`/`entry`/`st()` and `pushSuggestEntryToApp` all key on it — equivalences are exercised heavily in the `.mjs` tests.
6. **Schema field-name drift.** Persisted watchlist entries store synopsis under **`snippet`** and `tmdb_overview` (no `overview`); the dashboard projection uses `overview`, and scores are `tmdb_score` in JSON but `tmdbScore` in dashboard cards. Frontend normalization (`entryFromWatchlistEntry`) bridges them — do not "repair" the underlying keys.
7. **Cron wrapper `add_watchlist_cron.py` is a real gatekeeper.** It requires Plex configured (ownership source of truth, spec §1.2), runs `DailyWatchlistJob` (idempotent), rebuilds the dashboard, and diffs pending tmdb-id sets before/after to report exactly what was added; `--dry-run` scores/dedupes without writing; `--count N` (default 20) controls candidates per media type. Exit 0 even if nothing added.
8. **Config is env-driven with silent fallbacks.** `Config` reads `/workspace/.env` (falling back to `/app/.env`), then process env overrides. `WATCHLIST_STORE` defaults to `"json"` and any invalid value is coerced to `"json"` — flipping the store without setting the DB path (or vice versa) silently changes persistence. `validate_required()` requires Radarr/Sonarr keys + Plex token; without Plex, `auto_complete.py` hard-fails ("Plex not configured — cannot verify ownership").
9. **Daily pipeline is chained.** `daily_recommendations.py` (18:00 AEST cron) runs `auto_complete` first (moves Plex-present downloads pending→recommended), then category-rotation candidate processing, then `rebuild_dashboard.py` subprocess. Auto-complete validates via Radarr `hasFile`/Sonarr `has_episodes` **and** Plex ownership, keyed by stable `MediaIdentity` (`tmdb_id`/`imdb_id`), never bare title.
10. **Dashboard snapshot is a projection, not the store.** `dashboard-data.json` has `version:2` and adds `type`/`overview`/`tmdbScore`/`trailerUrl` that don't exist in the persisted entry — any test/consumer reading only `dashboard-data.json` sees a normalized view, not the raw model.
